# 开发计划文档骨架

按本骨架生成计划。「〔〕」内是填写说明，生成时替换为实际内容并删除说明本身；标注〔可选〕的段落按项目实际取舍。结构顺序不要打乱——执行会话依赖这个固定形状快速定位。

---

```markdown
# PLAN.md — 〔项目名〕〔本轮工作主题，如：仓库优化开发计划〕

> 职责边界：本文件承载**阶段性计划、待办与进度**；〔指向项目规则文件，如 AGENTS.md〕承载长期协作规则。〔项目指定设计事实源时：设计决策同步至 DESIGN.md 等指定文档，本文件记录执行落点与章节指针。〕
> 〔一句话说明本计划的来源：由某日的审查/需求分析产出，整合了哪些输入。〕
> **使用方式**：在当前会话连续推进已授权工作；作者选择换会话时，本计划也支持独立接手。普通 Phase 不要求另开窗口或逐步发送“继续”；高风险独立复核按本阶段安排由作者手动另开任务。文档入口为：① 项目规则文件（自动加载）；② 本文件「通用守则」；③ 本阶段章节；④ 该章点名的项目权威设计章节（若有）。无需恢复旧会话或阅读其它 Phase 全文，但仍须核对本阶段源码、依赖成果、适用的复核放行证据与测试。规格成熟度为「需细化」的条目先补规格，不得直接实施。
>
> 开场提示语：见下方「新会话开场提示词」（紧邻本文件头；作者手动创建会话时选择 Phase 推荐的 GPT 模型与推理强度）。

最近核实：〔日期〕（规划基线：〔实跑结果，或「未运行 + 原因」并注明历史结果日期；初始化写「由首个 Phase 建立」〕）。

## 新会话开场提示词（作者换会话或按复核安排另开任务时使用，把 N 换成本次编号）

〔本段置顶，供作者粘贴到已手动创建的会话。可复制代码块仅在首句出现一次「Phase N」，后文统一称「本阶段」或「本阶段章节」，不再设置阶段编号占位符。提示词只做「路由 + 硬约束」，细节在计划内维护；硬约束变化时同步本段，按项目裁剪且保持 ≤6 条。模型建议不授权另建、分叉或委派任务；确有协作需求时仅路由到该 Phase 已批准的约定。〕

\```text
请执行 〔项目名〕 开发计划中的 Phase N。

1. 先查 〔计划文件路径〕 的进度总览，完整阅读「通用守则」、本阶段章节与点名设计章节，并核对当前源码、依赖成果和测试。先识别阶段类型与授权：实施须满足「可执行 + 已纳入 + ⬜」、完整章节、前置依赖已完成且成果可用（含适用的复核放行证据）、阻塞决策已批准，以及第 2 条基线要求；复核按本章检查方法独立取证，先形成发现，再按既有授权收敛，只读任务不改文件。🔄 核对既有批准后接手，✅ 不重做，⛔ 按通用守则解阻。若为「需细化」，只补可执行规格，不写业务代码。
2. 代码实施前先跑本阶段规定的完整基线构建与测试，全绿才动手；不绿停止后续功能施工并报告，诊断及必要验证维护按通用守则处理，不改命令或跳过失败来制造全绿。初始化 Phase 尚无基线时，按已批准方案搭建并建立首个基线。纯路线图或文字更新可按「通用守则」记录未运行原因，此例外不适用于代码实施。
3. 「高风险：先方案后实现」阶段须先提出实施方案、经我确认后再写代码；已有明确批准且条件未变时引用结论，不重复询问。未批准的公共契约、依赖、产品取舍或风险边界变化才提交作者决策；普通技术选择由你核实、实施和验证，不要求我背书其可操作性。更新结论、日期和适用的设计事实源。
4. Git 按我的明确授权范围执行；未授权时不做写操作，只提供提交信息草稿。提交授权不自动包含推送、PR 或其它写操作，已明确授权的事项不重问。
5. 按「完成定义」核对交付物和全部验收证据；需要人工验收时，按本章「人工验收交付」提供候选、操作入口与手册，汇报「改了什么 / 为什么 / 是否引入风险」。自动验证通过但本阶段人工或发布验收未完成时，记录已通过项与待办，不标记已完成；全部门槛满足后再更新进度总览与「已完成」区。排查受阻按「连续执行与阻塞处理」执行。
6. 复核节点的执行方式、修复边界和放行条件按「复核与缺陷收敛」及本章安排执行。高风险独立复核由作者手动另开任务；已在该复核任务中直接执行，不再次要求换会话，也不自动创建、分叉或委派任务。未放行时停止依赖该结果的后续施工，独立且已授权的工作继续。
\```

## 通用守则（每个执行会话必读）

〔以下为默认集，按项目裁剪，保留计划执行所需的门槛与指针；全局协作规则沿用 AGENTS.md，不复制另一套。〕

1. **规划与实施基线**：近期可执行的存量代码阶段在规划时实跑〔项目规定的完整构建与测试命令〕；纯路线图或文字更新允许记录「未运行 + 原因」，不据此升级规格成熟度或宣称可开工。每个代码实施阶段先在当前代码上跑上述完整基线（本阶段另有规定时用本章命令），全绿再动手，不绿停止后续功能施工并报告；保留原命令与失败记录，不得改命令、跳过失败或降低门槛来制造全绿。可继续只读诊断及当前授权内必要、可逆的测试/验证设施维护，但须有定位证据，不改产品契约、依赖、安全约束、断言含义、覆盖范围或通过阈值；作者明确禁止的修改仍不得做。涉及产品高风险路径或真实范围扩张时先提交具体方案。维护后从头重跑原完整基线，全绿再恢复施工；本阶段新写代码的编译/测试失败按授权内调试修复，不逐次申请批准。记录日期、命令和实际通过/失败/跳过数，历史数字只作对照。〔初始化例外：尚无基线，由该 Phase 建立首个基线。〕
2. **修改纪律与开工门槛**：先核对前置依赖已完成且成果可用、适用的复核已放行、阻塞决策已批准，再按状态、规格与基线门槛实施。高风险实施先提出可审查方案、获作者确认后写码；已批准且条件未变的结论直接引用。只读复核按检查方法取证，不以实施基线失败禁止只读诊断，也不要求先申请写码批准。普通技术选择由 AI 核实和验证，不因有多个实现或必要支撑文件未列入初表就自动新增作者决策。区分产品实施清单和必要验证支撑，遵守明确禁止修改的边界；不顺手重构无关代码。
3. **Git 按明确授权执行**：未授权时不执行 git 写操作，交付**建议的提交信息草稿**（〔语言〕，讲清意图与影响）；作者已明确授权时执行对应操作，不重复询问。提交、推送、PR 等授权分别核对，不扩大到其它写操作或无关文件。**不新增第三方依赖**，除非对应作者决策已明确批准且条件未变。
4. **文档与完成状态**：公共行为变更同步〔XML 注释 / README / 对应文档〕，设计决策同步项目指定事实源，本文件记录执行落点。按完成定义核对全部交付物与验收证据，人工或发布验收未齐时记录已通过项和待办，保持进行中或如实标记阻塞；全部满足后才打 ✅ 并在「已完成」区留一行结论。每次暂停或结束汇报，最后用一句“下一步：……”写清最直接的动作、由谁执行、作者是否需操作；待人工验收时点名具体用例或所需回报，不能仅写“验收未齐”。已全部交付则说明无需操作；不会自动续跑时写明恢复条件，不承诺后台继续。仍有授权内可执行工作时先继续完成，不用该句代替执行。
5. 〔项目特有的文件/资源处置规则：临时资料怎么用、什么不许提交、什么不许写进哪些文档。没有则删除本条。〕
6. 〔访问限制：哪些目录被 deny 规则禁读（引用规则原文），哪些资源是显式授权的例外。没有则删除本条。〕
7. **行号免责**：本计划内的 `文件:行号` 为 〔基线日期〕 基线。若行号漂移，以**符号名（类/方法）**定位，并在汇报中指出偏差。
8. **连续执行与阻塞处理**：已授权工作持续推进；进度更新、工具返回、规格补写或上下文压缩不要求作者再说“继续”，也不要求新会话。失败后按证据调整方法，避免无新增证据的重复尝试；次数本身不是审批门槛。只有必要输入缺失、未批准的契约/范围/风险变化、权限阻挡或需要作者实际操作时，暂停受影响动作，先准备具体差异、证据、建议及所需决定，并指出适用规则；独立且已授权的工作继续。基线失败按第 1 条处理，不越过失败进入下游施工。
9. 〔项目不可破坏的不变量 / 强制注释规范等硬约束的指针，如"库内不变量见 AGENTS.md §5，任何时候不可破坏"。〕

### 复核与缺陷收敛

〔生成时按本计划的复杂度、失败后果、耦合、工作量、时间跨度、行为改动范围及测试充分性说明节点布局理由；区分机械修改与行为修改，不按固定分数、文件数或每几个 Phase 设置配额。以下规则按实际节点填写，节点细节单点维护在对应章节。〕

- 每个实施阶段完成前对照目标、不变量及验收场景自检。高风险改造完成后、关键接口广泛使用前、跨模块链路首次贯通时设置独立节点；重复覆盖可合并，但不能越过需要保护的依赖边界。
- 独立节点复用 Phase 结构，可用 `P2.R` 编号；总览「内容」注明复核，「依赖」引用前序成果及复核放行要求，不增加执行状态种类。前序按自身完成定义验收，复核依赖前序，下游依赖复核，禁止形成环。
- 高风险节点由作者手动另开任务，章节写明操作和开场提示词入口；其它节点默认当前会话。交接提供需求、批准设计、当前源码与测试入口，完成报告仅作线索；已在作者创建的复核任务中无需再次换会话。AI 不自动创建、分叉或委派任务。
- 从原始依据检查实际行为与测试断言；发现项记录预期/实际、触发条件、证据、影响及处置，未证实项保留核实方法。先形成发现，再在既有授权内修复和回归；只读要求优先，新契约、范围或风险取舍按作者决策处理。
- 阻塞问题未解决或关键证据缺失时，下游不得开工；只读审查报告交付不代表缺陷关闭或下游放行。非阻塞项写明暂缓理由及去向，涉及风险接受时由作者决定；附录 C 记录节点完成情况与单独的放行结论，独立且已授权的工作继续。
- 范围显著扩大、关键假设失效、同类缺陷反复出现或长期中断使证据可能失效时，重新核实当前代码与依赖，调整相关节点、覆盖范围和下游依赖并记录原因。时间和文件数量本身不触发审批，不重做仍有效且无关的验收。

## 进度总览

| Phase | 内容 | 建议模型 | 风险等级 | 依赖 | 规格成熟度 | 范围属性 | 执行状态 |
|---|---|---|---|---|---|---|---|
| P0 | 〔一句话〕 | 〔如 GPT-5.6 Terra / Medium〕 | 低/中/高/最高 | 无/PN | 可执行/需细化 | 已纳入/可选 | ⬜ 未开始 |
| … | | | | | | | |

状态口径：**执行状态**统一使用「图标 + 空格 + 中文状态」：⬜ 未开始 / 🔄 进行中 / ✅ 已完成 / ⛔ 阻塞（附一句原因）；直接写入表格单元格，不包行内代码，不使用纯文本、单独图标或任务复选框代替。**规格成熟度**只允许「可执行 / 需细化」；**范围属性**只允许「已纳入 / 可选」。三者不得混写。「可执行 + 已纳入 + ⬜」是必要条件，仍须满足完整章节、前置依赖、阻塞决策与适用的基线门槛，代码实施必须完整基线全绿（初始化例外）；🔄 在任务授权内连续推进或核对既有批准后接手，✅ 不重做，⛔ 按通用守则解阻。需细化先补规格，待验收不能提前标记已完成。

模型选择逻辑：按各 Phase 的复杂度、不确定性、失败后果、耦合和验证充分性选择，不固定默认 Astra。〔生成时依据 dev-plan 第 5 步将本计划实际采用的选型原则简述在此，删除本生成提示，使计划自包含；核实客户端名称与可用强度，遵从作者指定模型，不静默替换不可用模型。〕规划与实施分别判断，不能仅按文件类型选用较轻模型，规格与验收要求保持一致；执行中判断依据变化时重新评估。Ultra 的机制以当前客户端核实说明为准；若涉及自动委派，只有作者允许多代理且本阶段适合独立并行时才推荐；模型建议不切换当前执行模型，也不授予创建、分叉或委派任务的权限。

## Phase N：〔标题〕〔高风险实施加后缀：〔高风险：先方案后实现〕〕

**目标**：〔一句话，说结果不说过程〕。
**阶段类型**：〔实施 / 复核与缺陷收敛；后者同时明确「只读复核」或「复核并在既有授权内修复」〕。
**建议配置**：〔如 GPT-5.6 Sol / High；只选一个模型和强度，只有不直观时才补一句短理由〕。
**风险等级**：〔低/中/高/最高〕〔高及以上注明原因〕。
**前置依赖**：〔无，或前置 Phase / 作者决策及其所需成果、可核对的证据位置；依赖复核时须明确其放行结论，不能只检查节点是否已完成〕。

### 背景与证据

〔每条问题断言 = 现象 + 来源指针（代码 `文件:行号` / 项目权威设计章节 / 官方文档 / 实测记录）+ 核实日期 + 后果；点名设计章节时复述关键不变量，标出需核对的源码、依赖与测试入口。仅引用有助于实施的关键规则或对照样本；不得把临时报告当作执行前置阅读。〕

### 做什么 / 怎么做

〔按实际依赖写实施路径、契约、不变量、失败边界与验证安排，细节以风险和消除歧义的需要为准，不按模型档次决定详略。尚待选择方案的部分标记「需细化」，已定且可独立验收的内容另拆阶段；不能把候选方向当成可执行规格。高风险仍先方案后实现，已有批准且条件未变则引用结论。〕

### 作者决策点〔无则删除本节〕

〔只列需要作者决定的公共契约、依赖、产品取舍或风险边界差异：决策内容 + 候选项 + **建议值与理由**。多个合理技术实现本身不构成审批理由，技术可操作性由 AI 以源码和验证证明。明确阻塞整个 Phase 还是可分离的需细化部分；后者须与已定可执行内容划开。批准后改为「✅ 已定：<结论>（<日期>）」，同步项目指定设计事实源并记录执行落点。已批准且条件未变不重复询问。〕

### 禁止事项〔无则删除本节〕

〔本 Phase 容易"顺手多做"的事，明确划界。如：不要动某模块（那是 PX 的事）。〕

### 人工验收交付〔需要作者操作的阶段保留；否则删除〕

- **候选与入口**：〔交付哪些可运行产物，如何关联代码/构建、适用配置与手册；填写真实产品入口及候选标识/构建时间的核对方法。待建入口标明落实文件和交付前核验方法，不当作已可用事实〕。
- **环境与工具**：〔优先复用的环境、脚本和页面；缺口所需的最小工具、用途、文件范围及资源隔离；准备/启动、就绪核验、正常停止与清理入口，缺失依赖怎样提示和处理。跨阶段复用，正式产品入口可用后承接正常业务操作〕。
- **手册与覆盖**：〔手册路径；本阶段必验、受影响回归及长时间运行/真实设备等专项，明确所属阶段和完成门槛。正常路径使用真实产品能力，标明模拟/注入/种子数据等替代范围与证据限制，不将演示当成集成通过〕。
- **结果与重验**：〔手册、运行入口与结果记录对应同一候选的方法；作者需回报的操作、观察和证据。修复或换候选后说明必重验项、可保留的旧证据及理由；人工结果与 AI 复核、自动测试分别记录〕。

### 如何验证

〔可执行命令 + 预期结果，列出必须覆盖的行为、边界与失败场景及判断标准。实施阶段包含目标、不变量与实际行为的自检；复核不能只重跑测试，还需核对需求、批准设计、实现及断言的一致性。记录实际通过/失败/跳过数，不规定无依据的新增用例数量。人工或发布验收适用时写明操作、预期及证据记录方式；验证在本阶段内完成，不默认留到后续阶段。〕

### 复核安排〔仅独立复核节点保留〕

- **设置理由与覆盖范围**：〔为什么在此设点；覆盖的前序成果、模块/行为与不覆盖项，避免机械全仓审查〕。
- **设计依据与检查方法**：〔点名需求/批准设计章节，复述关键不变量，给出当前源码/测试入口；写清要核对的预期行为、失败边界、集成路径及取证方法，可执行命令维护在「如何验证」〕。
- **执行方式**：〔高风险：作者手动创建新任务，将置顶提示词的 N 替换为本节点编号；已在该复核任务内直接执行。其它节点：当前会话执行。不得自动创建或委派任务〕。
- **证据与修复边界**：〔发现项按「预期/实际、触发条件、证据、影响、处置」记录；哪些只审查，哪些可按既有授权修复，哪些须提交作者决策。修复后复验触发路径及受影响回归〕。
- **放行条件与下游**：〔点名受约束的后续阶段及必需证据，定义阻塞问题和非阻塞项的处置条件；检查范围内无阻塞问题且关键证据齐备才放行。只读报告完成但尚有阻塞问题时，记录未放行并阻塞相应下游，修复落入明确的后续安排〕。

### 完成定义

〔逐项列出：交付物、自动验证、适用的人工/发布验收及证据、文档同步、汇报和提交信息草稿。有人工验收时，包含已核验的可操作候选、准备/退出清理入口与匹配手册；候选交付不等于作者已验收。实施包含阶段内自检；独立复核按本章的只读/修复范围验收并记录单独的下游放行结论，不能因报告已交付就宣称缺陷已关闭。只读任务不修改文件，其结果通过回复交付，由有文档写入授权的任务登记状态和证据。全部门槛满足才将进度标为 ✅ 并写入已完成区；自动验证通过但人工/发布验收未完成时，记录已通过项和剩余待办，不代替作者签收。〕

## 常见走样与纠正

写完对照检查，这些是其它会话写计划时最常见的质量滑坡：

- **章节互相引用**（"参见 P3 的分析"）→ 违反自包含，把内容复制过去或重写。
- **验证空话**（"确保功能正常""充分测试"）→ 改为命令 + 预期输出。
- **替作者拍板**（直接写"删除 X 模块"而它是公共 API）→ 改为决策点 + 建议值。
- **每个 Phase 都堆模型说明** → 收成一行 `模型 / 强度`，只在不直观时补一句理由。
- **全部默认最强模型或只按文件类型分档** → 按各阶段实际判断负担与失败后果选型，常规开发可用 Sol，局部明确任务可考虑 Terra / Luna，高风险优先考虑 Astra；保留相同的规格与验收门槛。
- **写内部参数名或回退方案** → 改用 Codex 客户端可见名称；除非作者明确要求，否则不写回退。
- **证据失踪**（"存在并发问题"无来源指针无日期）→ 当场核实或标「待核实 + 方法」。
- **输入黑洞**（未采纳建议无去向或全塞入 backlog）→ 在附录 A 标明处置、理由和去向，仅暂缓项进入附录 B。
- **两份计划并行**（无视既有 PLAN/TODO 文件另起炉灶）→ 合并吸收，单一事实源。
- **状态样式不一致**（纯文本「未开始」、单独图标或任务复选框）→ 按状态口径统一为图标加中文文字；更新既有总览时一并统一展示，不改变实际执行状态。
- **状态列超载**（`⬜ 路线图`、`⬜ 可选路线图`、`待细化`写进依赖）→ 拆成「执行状态 / 规格成熟度 / 范围属性」三列；依赖只写真实前置 Phase 或明确的作者决策点。
- **拿路线图直接施工**（只有一行意图就开始写代码）→ 开场提示拦截；在当前授权内核实源码与依赖、补全规格；需批准的实施方案确认后再写代码，不强制另开细化会话。
- **把每个步骤变成审批** → 普通技术选择、必要验证维护和自写代码调试在授权内完成，实际契约/范围/风险变化才提交作者。
- **用交接模板结束可继续的任务** → 当前授权内持续推进，仅在作者换会话或要求复制时交付开场提示词。
- **只报“未完成”却没有行动指引** → 最后补一句具体“下一步”，如“下一步：请按验收手册 A1 执行一次断线恢复，并回报观察结果”；不把“请继续”作为常规前置操作。
- **以强模型代替完整规格** → 补齐契约、不变量、失败边界与验收，未决方案仍由作者拍板。
- **规划免跑被用于实施** → 实施前完整基线必须全绿，初始化按明确例外建立首个基线。
- **状态通过就施工或提前完成** → 检查依赖成果与阻塞决策；自动验证通过不代替本阶段人工或发布验收。
- **每阶段重建验收网页 / 只交手册却无可用入口** → 按实际缺口补最小工具并优先复用；交付前核实候选可操作，明确启动、停止和清理，不制造无必要的环境工作。
- **模拟演示当集成通过 / 新候选直接沿用旧结果** → 明示替代范围，绑定候选、入口、手册与证据，按改动影响重验，保留仍有效的无关证据。
- **机械安排 review 或全部留到末尾** → 按实际风险、耦合和依赖边界设点；机械批量修改不因文件多自动升级，少量高风险修改仍须专项复核。
- **测试全绿就宣布设计一致 / 审查完成就放行** → 对照需求和批准设计取证，分别记录发现、修复状态与下游放行结论；证据缺失如实保留。
- **复核自己依赖自己 / 只读任务顺手修复** → 前序、复核、下游单向依赖；只读要求优先，节点和报告不扩大授权。
