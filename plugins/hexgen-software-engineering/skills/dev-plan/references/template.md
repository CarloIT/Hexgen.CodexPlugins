# 开发计划文档骨架

按本骨架生成计划。「〔〕」内是填写说明，生成时替换为实际内容并删除说明本身；标注〔可选〕的段落按项目实际取舍。结构顺序不要打乱——执行会话依赖这个固定形状快速定位。

---

```markdown
# PLAN.md — 〔项目名〕〔本轮工作主题，如：仓库优化开发计划〕

> 职责边界：本文件承载**阶段性计划、待办与进度**；〔指向项目规则文件，如 AGENTS.md〕承载长期协作规则。〔项目指定设计事实源时：设计决策同步至 DESIGN.md 等指定文档，本文件记录执行落点与章节指针。〕
> 〔一句话说明本计划的来源：由某日的审查/需求分析产出，整合了哪些输入。〕
> **使用方式**：作者为每个可执行 Phase 开启独立新会话。文档入口为：① 项目规则文件（自动加载）；② 本文件「通用守则」；③ 本阶段章节；④ 该章点名的项目权威设计章节（若有）。无需恢复旧会话或阅读其它 Phase 全文，但仍须核对本阶段源码、依赖成果与测试。规格成熟度为「需细化」的条目先补规格，不得直接实施。
>
> 开场提示语：见下方「新会话开场提示词」（紧邻本文件头；作者手动创建会话时选择 Phase 推荐的 GPT 模型与推理强度）。

最近核实：〔日期〕（规划基线：〔实跑结果，或「未运行 + 原因」并注明历史结果日期；初始化写「由首个 Phase 建立」〕）。

## 新会话开场提示词（作者粘贴用：每开一个 Phase 复制一次，把 N 换成本次编号）

〔本段置顶，供作者粘贴到已手动创建的会话。可复制代码块仅在首句出现一次「Phase N」，后文统一称「本阶段」或「本阶段章节」，不再设置阶段编号占位符。提示词只做「路由 + 硬约束」，细节在计划内维护；硬约束变化时同步本段，按项目裁剪且保持 ≤6 条。模型建议不授权另建、分叉或委派任务；确有协作需求时仅路由到该 Phase 已批准的约定。〕

\```text
请执行 〔项目名〕 开发计划中的 Phase N。

1. 先查 〔计划文件路径〕 的进度总览，完整阅读「通用守则」、本阶段章节与点名设计章节，并核对当前源码、依赖成果和测试。实施须满足「可执行 + 已纳入 + 🟪」、完整章节、前置依赖已完成且成果可用、阻塞决策已批准，以及第 2 条基线要求；🔄 仅在我明确续做时按同样门槛恢复，✅ 不重做，⛔ 先解阻。若为「需细化」，只补可执行规格，不写业务代码。
2. 代码实施前先跑本阶段规定的完整基线构建与测试，全绿才动手；不绿立即停止实施并报告，不改命令或跳过失败来制造全绿。初始化 Phase 尚无基线时，按已批准方案搭建并建立首个基线。纯路线图或文字更新可按「通用守则」记录未运行原因，此例外不适用于代码实施。
3. 「高风险：先方案后实现」阶段须先提出实施方案、经我确认后再写代码；已有明确批准且条件未变时引用结论，不重复询问。公共契约、依赖及存在多个合理方案等「作者决策点」仍逐项找我拍板，并更新结论、日期和适用的设计事实源。
4. git 一律由我本人操作：你不要执行 commit/push 等任何 git 写操作，完成后把建议的提交信息草稿给我即可。
5. 按「完成定义」核对交付物和全部验收证据，汇报「改了什么 / 为什么 / 是否引入风险」。自动验证通过但本阶段人工或发布验收未完成时，记录已通过项与待办，不标记已完成；全部门槛满足后再更新进度总览与「已完成」区。排查受阻按「卡住升级原则」处理。
\```

## 通用守则（每个执行会话必读）

〔以下为默认集，按项目裁剪，保留计划执行所需的门槛与指针；全局协作规则沿用 AGENTS.md，不复制另一套。〕

1. **规划与实施基线**：近期可执行的存量代码阶段在规划时实跑〔项目规定的完整构建与测试命令〕；纯路线图或文字更新允许记录「未运行 + 原因」，不据此升级规格成熟度或宣称可开工。每个代码实施阶段先在当前代码上跑上述完整基线（本阶段另有规定时用本章命令），全绿再动手，不绿立即停止实施并报告；不得改命令、跳过失败或降低门槛来制造全绿。记录日期、命令和实际通过/失败/跳过数，历史数字只作对照。〔初始化例外：尚无基线，由该 Phase 建立首个基线。〕
2. **修改纪律与开工门槛**：先核对前置依赖已完成且成果可用、阻塞决策已批准，再按状态、规格与基线门槛实施。高风险先提出方案、获作者确认后写码；已批准且条件未变的结论直接引用。改动范围与汇报遵循项目规则，不顺手重构无关代码。
3. **Git 一律由作者（人类）主导**：AI 不执行任何 git 写操作（不 commit、不 push、不建 PR）；Phase 完成后附**建议的提交信息草稿**（〔语言〕，讲清意图与影响），由作者自行提交。**不新增第三方依赖**，除非对应作者决策已明确批准且条件未变。
4. **文档与完成状态**：公共行为变更同步〔XML 注释 / README / 对应文档〕，设计决策同步项目指定事实源，本文件记录执行落点。按完成定义核对全部交付物与验收证据，人工或发布验收未齐时记录已通过项和待办，保持进行中或如实标记阻塞；全部满足后才打 ✅ 并在「已完成」区留一行结论。
5. 〔项目特有的文件/资源处置规则：临时资料怎么用、什么不许提交、什么不许写进哪些文档。没有则删除本条。〕
6. 〔访问限制：哪些目录被 deny 规则禁读（引用规则原文），哪些资源是显式授权的例外。没有则删除本条。〕
7. **行号免责**：本计划内的 `文件:行号` 为 〔基线日期〕 基线。若行号漂移，以**符号名（类/方法）**定位，并在汇报中指出偏差。
8. **卡住升级原则**：在已批准方向内，有新证据且下一步可逆时继续排查；同一问题连续两次尝试无新增证据，或下一步涉及新方案、额外权限、风险变化时，停止相关动作并向作者说明证据、已尝试内容及建议，由作者决定下一步；独立且已授权的工作可继续。基线不绿仍按第 1 条立即停止实施。
9. 〔项目不可破坏的不变量 / 强制注释规范等硬约束的指针，如"库内不变量见 AGENTS.md §5，任何时候不可破坏"。〕

## 进度总览

| Phase | 内容 | 建议模型 | 风险等级 | 依赖 | 规格成熟度 | 范围属性 | 执行状态 |
|---|---|---|---|---|---|---|---|
| P0 | 〔一句话〕 | 〔如 GPT-6 Astra / Extra High〕 | 低/中/高/最高 | 无/PN | 可执行/需细化 | 已纳入/可选 | 🟪 未开始 |
| … | | | | | | | |

状态口径：**执行状态**统一使用「图标 + 空格 + 中文状态」：🟪 未开始 / 🔄 进行中 / ✅ 已完成 / ⛔ 阻塞（附一句原因）；直接写入表格单元格，不包行内代码，不使用纯文本、单独图标或任务复选框代替。**规格成熟度**只允许「可执行 / 需细化」；**范围属性**只允许「已纳入 / 可选」。三者不得混写。「可执行 + 已纳入 + 🟪」是必要条件，仍须满足完整章节、前置依赖、阻塞决策与适用的基线门槛，代码实施必须完整基线全绿（初始化例外）；🔄 仅在明确续做时按同样门槛恢复，✅ 不重做，⛔ 先解阻。需细化先补规格，待验收不能提前标记已完成。

模型选择逻辑：默认 `GPT-6 Astra / 推理强度`。机械任务从 Medium、跨层正确性任务从 High、高风险任务从 Extra High 起，按风险与复杂度调整；不据此省略规格或降低验收要求。〔生成时核实客户端名称与可用强度；作者另有模型要求时按其要求填写，不静默替换不可用模型。〕Ultra 的机制以当前客户端核实说明为准，仅在作者允许多代理且本阶段适合独立并行时推荐；模型建议不授予创建、分叉或委派任务的权限。

## Phase N：〔标题〕〔高风险加后缀：〔高风险：先方案后实现〕〕

**目标**：〔一句话，说结果不说过程〕。
**建议配置**：〔如 GPT-6 Astra / High；只有不直观时才补一句短理由〕。
**风险等级**：〔低/中/高/最高〕〔高及以上注明原因〕。
**前置依赖**：〔无，或前置 Phase / 作者决策及其所需成果、可核对的证据位置〕。

### 背景与证据

〔每条问题断言 = 现象 + 来源指针（代码 `文件:行号` / 项目权威设计章节 / 官方文档 / 实测记录）+ 核实日期 + 后果；点名设计章节时复述关键不变量，标出需核对的源码、依赖与测试入口。仅引用有助于实施的关键规则或对照样本；不得把临时报告当作执行前置阅读。〕

### 做什么 / 怎么做

〔按实际依赖写实施路径、契约、不变量、失败边界与验证安排，细节以风险和消除歧义的需要为准，不按模型档次决定详略。尚待选择方案的部分标记「需细化」，已定且可独立验收的内容另拆阶段；不能把候选方向当成可执行规格。高风险仍先方案后实现，已有批准且条件未变则引用结论。〕

### 作者决策点〔无则删除本节〕

〔逐条：决策内容 + 候选项 + **建议值与理由**，存在多个合理方案仍由作者拍板。明确阻塞整个 Phase 还是可分离的需细化部分；后者须与已定可执行内容划开。批准后改为「✅ 已定：<结论>（<日期>）」，同步项目指定设计事实源并记录执行落点。已批准且条件未变不重复询问。〕

### 禁止事项〔无则删除本节〕

〔本 Phase 容易"顺手多做"的事，明确划界。如：不要动某模块（那是 PX 的事）。〕

### 如何验证

〔可执行命令 + 预期结果，列出必须覆盖的行为、边界与失败场景及判断标准。记录实际通过/失败/跳过数，不规定无依据的新增用例数量。人工或发布验收适用时写明操作、预期及证据记录方式；验证在本阶段内完成，不默认留到后续阶段。〕

### 完成定义

〔逐项列出：交付物、自动验证、适用的人工/发布验收及证据、文档同步、汇报和提交信息草稿。全部门槛满足才将进度标为 ✅ 并写入已完成区；自动验证通过但人工/发布验收未完成时，记录已通过项和剩余待办，不代替作者签收。〕

## 常见走样与纠正

写完对照检查，这些是其它会话写计划时最常见的质量滑坡：

- **章节互相引用**（"参见 P3 的分析"）→ 违反自包含，把内容复制过去或重写。
- **验证空话**（"确保功能正常""充分测试"）→ 改为命令 + 预期输出。
- **替作者拍板**（直接写"删除 X 模块"而它是公共 API）→ 改为决策点 + 建议值。
- **每个 Phase 都堆模型说明** → 收成一行 `GPT-6 Astra / High`，只在不直观时补一句理由。
- **写内部参数名或回退方案** → 改用 Codex 客户端可见名称；除非作者明确要求，否则不写回退。
- **证据失踪**（"存在并发问题"无来源指针无日期）→ 当场核实或标「待核实 + 方法」。
- **输入黑洞**（未采纳建议无去向或全塞入 backlog）→ 在附录 A 标明处置、理由和去向，仅暂缓项进入附录 B。
- **两份计划并行**（无视既有 PLAN/TODO 文件另起炉灶）→ 合并吸收，单一事实源。
- **状态样式不一致**（纯文本「未开始」、单独图标或任务复选框）→ 按状态口径统一为图标加中文文字；更新既有总览时一并统一展示，不改变实际执行状态。
- **状态列超载**（`🟪 路线图`、`🟪 可选路线图`、`待细化`写进依赖）→ 拆成「执行状态 / 规格成熟度 / 范围属性」三列；依赖只写真实前置 Phase 或明确的作者决策点。
- **拿路线图直接施工**（只有一行意图就开始写代码）→ 开场提示拦截；先开细化会话，核实当前代码与依赖并补全完整 Phase 章节。
- **以强模型代替完整规格** → 补齐契约、不变量、失败边界与验收，未决方案仍由作者拍板。
- **规划免跑被用于实施** → 实施前完整基线必须全绿，初始化按明确例外建立首个基线。
- **状态通过就施工或提前完成** → 检查依赖成果与阻塞决策；自动验证通过不代替本阶段人工或发布验收。
