# dev-plan — 分阶段开发计划文档

产出一份**当前会话能持续执行、新会话也能独立接手**的开发计划。Phase 是范围与验收单位，不是强制切换会话的单位；通常由作者选择是否另开会话，高风险独立复核按第 3 步安排作者手动另开任务。计划承载阶段目标、执行安排与进度；项目规则指定 `DESIGN.md` 等设计事实源时，路由到其**点名章节**。自包含指无需恢复旧会话或临时报告，执行者仍须核对本阶段涉及的当前源码、依赖与测试。全局协作规则沿用 AGENTS.md，不在技能中维护另一套。

## 核心原则（先理解为什么，再动笔）

1. **计划支持冷启动，但不要求冷启动**。每个可执行 Phase 就地写清做法、依赖、验证与完成定义；背景证据就地给出，或点名项目权威设计章节并复述关键不变量。不得依赖"见上文"、临时报告或会话外口头共识。自测法：从「通用守则 + 该章 + 点名设计章节」出发，执行者能否找到需核对的源码与测试，并判断开工条件是否满足？

2. **证据先于计划**。计划质量的上限是它背后核实工作的质量。每个"问题断言"必须带**可核查的来源指针**（代码 `文件:行号` / 设计文档章节 / 官方文档 URL / 实测记录）和核实日期；没核实过的不准写成事实，要么当场核实，要么显式标注「待核实 + 核实方法」。涉及代码行号的，写上行号免责条款（行号是某日基线，漂移后按符号名定位）——这让计划经得起代码演进。

3. **规格成熟度与模型能力分开**。可执行的实施 Phase 必须明确目标、契约、不变量、实施路径、失败边界与验收，不因模型更强而省略规格。尚待选择方案的部分标记「需细化」；可独立推进的已定内容拆为可执行 Phase。细节深度取决于任务风险和防止歧义的需要，模型配置按第 5 步选择。

4. **作者决定目标、契约与风险边界，AI 负责边界内的技术判断**。新增或变更公共契约、第三方依赖、安全/数据/商业/法律边界，以及需要作者取舍的产品行为，列为「作者决策点」：写清选项、**建议值与理由**、阻塞范围和可审查的实施方案。多个合理实现、换一种诊断方法、补测试同步或修复自写代码错误，本身不构成审批理由；在已授权范围内由 AI 核实、选择、验证并报告。批准后就地记录结论与日期；已批准且条件未变不重复询问，也不把应由源码和测试证明的可操作性转交作者背书。项目指定设计事实源时，设计决策同步到该文档，PLAN.md 记录执行落点与章节指针。

5. **验证必须可执行**。写清命令、预期结果及需要覆盖的行为、边界和失败场景，例如「取消后任务退出，资源可重新获取」。记录实际通过、失败与跳过数，不设无依据的新增用例数量配额。完成定义逐项列出交付物和验收门槛；人工或发布验收属于本阶段时，证据未齐不得标记已完成，自动验证通过不代替作者签收。

6. **不静默丢弃任何输入**。审查报告、建议和旧待办逐条标记「采纳 / 暂缓 / 不采纳 / 已失效 / 重复合并」，写清理由与去向。采纳指向 Phase，暂缓进入 backlog，不采纳或已失效记录依据，重复项指向合并后的条目；不把所有未采纳意见都塞入 backlog。涉及取舍时仍按作者决策边界确认。

7. **路线图不是可执行 Phase**。分开记录三个维度：① 执行状态：⬜ 未开始 / 🔄 进行中 / ✅ 已完成 / ⛔ 阻塞；② 规格成熟度：可执行 / 需细化；③ 范围属性：已纳入 / 可选。首次实施须满足「可执行 + 已纳入 + 未开始」、完整章节、前置依赖已完成且成果可用、阻塞决策已批准；代码实施另须当前完整基线全绿（初始化例外）。进行中的阶段在当前任务授权内持续推进；新执行者接手时核对任务范围、已有批准、当前代码与验证证据，不要求作者重批未变事项。已完成不重做，阻塞先解阻，需细化先补规格，不得凭状态表或路线图摘要直接施工。

8. **授权内连续推进，实际越界才停问**。用户要求处理某阶段后，应完成该阶段已授权且可执行的工作；进度更新、规格补写、普通编译/测试调试、工具返回和上下文压缩都不是要求用户再说“继续”的节点。细化授权不等于高风险实施批准，不自动推进其它阶段。只在缺少必要输入、出现未批准的契约/范围/风险变化、权限阻挡或需要作者实际操作时暂停受影响动作，同时完成独立且已授权的工作。提问前先形成具体方案，指出需要作者决定的差异和适用规则；按实际决策合并问题，不为每个技术步骤另编号审批。

## 两类计划：先认清场景

写计划前先判断属于哪一类，它决定「基线」「证据」「首个 Phase」怎么写：

- **存量优化型**（基于现有代码做重构 / 修缺陷 / 优化）：近期可执行阶段在规划时实跑项目规定的完整构建与测试，记录到附录 C；纯路线图或文字更新可写「未运行 + 原因」，不据此升级规格成熟度或宣称可开工。每个代码实施阶段仍须先在当前代码上跑完整基线，全绿才动手；不绿立即停止后续功能施工并报告，诊断与维护边界见下文。证据 = `文件:行号` + 核实日期。
- **绿地起步型**（从零新建项目 / 模块）：**尚无代码，没有基线可跑**——首个 Phase 通常是「搭骨架 + 接底座 + 建立首个基线」，此后各 Phase 以它为对照原点；证据锚定**设计文档章节**（如 DESIGN.md §x）、官方文档或实测记录，而非代码行号；通用守则的「开工先跑基线」与开场提示词须给初始化 Phase 留例外（它没有上一手基线）。附录 C 如实写「绿地，基线由首个 Phase 建立」。

两者可在同一大项目里按 Phase 并存（如先绿地搭新模块、再优化既有模块）。裁剪通用守则时按各 Phase 的实际场景取舍，不要硬套不存在的基线。

**失败后的边界**：保留原命令、失败日志与结果，停止依赖失败门禁的后续功能施工；可继续只读诊断，以及当前授权内必要、可逆的测试/验证设施维护。维护须有定位证据，不改产品契约、依赖、安全约束、断言含义、覆盖范围或通过阈值；不能通过跳过、放宽或反复重跑碰绿掩盖问题。维护完成后从头重跑原完整基线，全绿后才恢复后续施工。若修复涉及产品高风险路径、真实范围扩张或作者明确禁止的文件，则提交具体差异等候批准；不得用“测试维护”覆盖只读、禁止改测试等明确限制。计划中的文件清单应区分产品实施边界与必要验证支撑，不因支撑文件未列入初表就自动新增审批。

本阶段新写的代码或验证设施编译/测试失败，属于授权范围内的实现调试；按证据修复并重跑相应原验证，不把每次失败都升级为作者决策。无新增变化或疑点时不机械重复已通过检查；当前源码、依赖或环境变化影响原证据时须重新验证，历史基线不能替代当前基线。

## 工作流程

### 第 1 步：核实输入

- 收集本次计划的全部输入源：审查结论、需求描述、既有待办、他人建议文档。
- 对问题断言读码、查文档或实测核实，记录日期；基线是否实跑按上方计划类型处理。记录完整命令、实测结果与日期；未运行须说明原因，历史结果注明原日期，不冒充本次验证。规划基线不替代实施前基线，不修改命令、跳过失败或降低门槛来制造全绿。
- 输入中已失效/与现状矛盾的内容，修正后再用，并在交付时向作者指出（这经常发生：文档比代码老）。

### 第 2 步：确定文件位置与合并策略

- 计划文件位置遵守项目约定（很多项目的 AGENTS.md 会指定，如根目录 `PLAN.md`）；无约定时默认仓库根目录 `PLAN.md`。
- **动笔前先找既有计划文件并通读**：吸收其未完成待办与已完成台账进新计划，绝不让两份计划并行存在。
- 语言跟随项目文档语言（本用户默认中文）。

### 第 3 步：切分 Phase

- 粒度 = 有明确边界、可独立验收且便于接手的工作量（含基线、实现、验证、汇报）；不因模型增强机械扩大 Phase。
- 按实际依赖与风险安排顺序，不套用固定话题顺序；验证随所属 Phase 完成，不默认留到末尾集中补测试。
- 相关机械工作可合并；高风险改造独立成章并标注「高风险：先方案后实现」。已批准且条件未变的实施方案可直接引用，不重新走审批。
- 写清 Phase 间依赖（如"公共 API 定稿须在底座重构前"），没有依赖就标"无"；独立性不自动授权另开会话或并行代理。
- 允许把远期、依赖尚不稳定的工作保留为「需细化」路线图，但每条至少写清阶段意图、当前最小依赖、范围属性（已纳入 / 可选）与细化触发条件；不得给路线图条目伪造可执行规格，也不得用「待细化」代替依赖。

#### 安排复核与缺陷收敛

- **按风险混合安排**：综合需求复杂度、失败后果、跨模块耦合、工作量、时间跨度、受影响文件与测试充分性，说明选择节点的关键理由。区分机械修改与行为修改，不用固定分数、文件数量或每隔几个 Phase 的配额代替判断；少量文件中的高风险行为不能被其它低风险因素抵消。
- **每阶段自检，关键边界专项复核**：实施阶段结束前，在「如何验证 / 完成定义」中对照目标、不变量与验收场景核实实际行为。高风险改造完成后、关键接口被后续阶段广泛使用前、跨模块业务链路首次贯通时安排独立复核；相邻且覆盖范围一致的节点可合并，但不能因此推迟到依赖成果已被广泛使用之后。复核检查设计一致性、功能缺陷、失败边界及集成行为，不能以测试全绿或实现者的完成报告代替。
- **节点可执行、依赖不成环**：独立节点复用 Phase 章节及现有状态、规格与范围属性，可用 `P2.R` 等编号避免重排；明确设置理由、覆盖范围、设计依据、检查方法、证据要求、修复边界、放行条件与受约束的后续阶段。前序实施按自己的完成定义验收，复核依赖其成果，下游依赖复核放行；不要让前序完成又依赖后置复核。只做阶段内自检时无需增加独立节点。
- **高风险复核由作者另开任务**：在节点内写明作者手动创建新任务、使用既有开场提示词的入口及编号，原任务交接后等待该节点的放行证据；已在作者创建的复核任务中则直接执行，不再要求另开。其它节点默认在当前会话执行；不得自动创建、分叉或委派任务。复核者从需求、已批准设计、当前源码与测试独立取证，原实现报告仅作线索。
- **先取证，再按授权收敛**：发现项记录预期与实际差异、触发条件、来源证据、影响及处置；未证实的问题写「待核实 + 核实方法」。在节点中区分「只读复核」与「复核并在既有授权内修复」，计划安排本身不扩大修改权限；只读任务不得改文件或修代码。先形成发现，再按已有授权修复并验证复现路径与受影响回归；新增契约、范围或风险取舍仍按作者决策边界处理。测试也可能偏离设计，必要时核对断言与批准契约，而非仅重跑同一组测试。
- **按证据放行**：阻塞问题未解决或关键证据缺失时，不放行依赖该结果的阶段；独立且已授权的工作继续。非阻塞项记录暂缓理由与去向，风险接受涉及作者取舍时仍由作者决定。节点按已确定的复核/修复范围定义完成，记录审查已完成与下游未放行的区别；只读审查交付报告不等于缺陷已关闭。实际验证、未验项和放行结论写入附录 C，不以「未发现问题」保证无缺陷。
- **执行中重新评估**：实际范围显著扩大、关键假设失效、同类缺陷反复出现，或长时间间隔可能使证据失效时，重新核对当前代码与依赖，调整节点位置、覆盖范围及下游依赖，记录原因；既有结论受到影响时重验相关部分。时间和文件数量本身不触发审批，只有实际授权边界变化才提交作者决策；不因新增节点重做无关且仍有效的验收。

#### 安排人工验收交付

- **按阶段需要安排**：功能交互、业务链路或真实环境行为需要作者判断时，将人工验收及可直接操作的候选交付纳入该阶段；纯文档、机械修改等无需人为增加服务端或网页。AI 的设计/代码复核与作者人工验收分别取证，不能互相代替。
- **优先复用，缺口进计划**：复用现有环境、启动脚本和产品入口；不足时才规划最小验收页面、命令行入口或模拟设施，写清用途、文件落点及授权范围，不默认每阶段另建一套。跨阶段沿用并维护工具，正式产品入口可用后，正常业务操作转到正式入口；专项工具可保留用于故障注入和边界验证。
- **交付可操作候选**：在本章明确候选产物、入口、准备/启动、正常停止与清理、手册和证据位置。准备尽量简化为一条命令或少量明确操作；交付前核实构建/启动及入口可用性，提供地址或操作入口、可核对的候选标识与构建时间（适用时），说明缺失依赖的提示和处理。规划中的待建入口写落实位置与核验方法，不冒充当前已可用；具体脚本、页面和资源隔离由项目实现。
- **证明真实路径**：正常流程应调用本次候选的真实产品能力；标明模拟设备、故障注入、种子数据、模拟时间等替代了哪一段，以及证据不能覆盖什么。纯原型或模拟演示可以作为已约定的阶段目标，但不得据此宣称实际后端、真实设备或完整产品已通过。
- **范围与证据绑定**：手册按本阶段必验、受影响回归、长时间运行/真实设备等专项分组，写明哪些属于本阶段完成门槛、哪些已明确归入后续阶段。手册、运行入口和结果记录须能对应同一候选；修复或更换候选后按影响说明重验项与仍有效的旧证据，不机械全量重验。手册细节由 manual-acceptance-guide 承载；候选交付、AI 自检通过与作者验收完成分别记录，证据未齐不提前完成。

### 第 4 步：按骨架填充

读取并套用 [references/template.md](references/template.md) 的完整骨架（文件头 / 开场提示词 / 通用守则 / 进度总览表 / Phase 章节 / 三个附录 / 已完成区）。开场提示词置顶（紧邻文件头），供作者主动切换会话或按高风险独立复核安排另开任务时使用；普通阶段的连续执行不以交接为前置条件。骨架中各占位符的填写要求都注释在模板里。

- 进度总览的「执行状态」格统一使用「图标 + 空格 + 中文状态」：⬜ 未开始、🔄 进行中、✅ 已完成、⛔ 阻塞；阻塞时附一句原因。直接写入 Markdown 表格，不包行内代码，不使用纯文本、单独图标或任务复选框代替。新建计划与更新既有总览时均按此格式填写，状态判断仍遵守原有开工与验收门槛。
- 默认将新会话开场提示词视为作者粘贴到**已经手动创建的会话**的内容；不得仅因模型或推理强度建议要求执行 AI 再次创建、分叉或委派会话。若某个 Phase 确有隔离、并行或交接需求，将目标、授权边界、会话数量、工作区策略和汇总方式写入该 Phase，必要时列为作者决策点；通用开场提示词只路由到该约定，不重复或扩大授权。
- 可复制的开场提示词仅在首句出现一次 `Phase N`，后文统一称「本阶段」或「本阶段章节」，不再引入需替换的阶段编号占位符，让作者只改一次 `N`。

### 第 5 步：标注明确的模型与推理强度

1. **逐 Phase 选型，不固定默认模型**。综合复杂度、不确定性、失败后果、跨模块耦合和验证充分性，在满足质量要求的前提下兼顾成本与速度；无需作者先要求节省成本才推荐其他模型。常规开发优先考虑 Sol，明确且局部的任务考虑 Terra / Luna，高风险或需要深入探索的任务优先考虑 Astra；作者指定模型时遵从其要求，能力或可用性存在疑点时说明并提出建议。
2. 用作者当前提供的列表或客户端可核实信息确认模型与强度；官方文档用于补充能力和机制，不能代替账号可用性证据。不写死可用档位清单，不把内部参数名当成界面名称；无法确认时标注建议待核实，不因配置建议不明而中断当前可执行工作。模型不可用时说明限制并提交替代建议，不静默替换。
3. 每个 Phase 只写一行 **建议配置**：客户端模型短名称 + 可见强度，例如 `GPT-5.6 Sol / Medium`。进度总览合并到「建议模型」列，不另列强度、不写 slug；回退方案仅在作者要求时补充。规划任务与各实施 Phase 分别选型，制定复杂计划使用 Astra 不意味着所有实施阶段也使用 Astra。
4. 下表是工程建议起点，不是实测能力保证或固定等级表；根据本阶段实际风险调整，模型与推理强度分别判断，不为凑齐模型而强行分配，也不靠提高强度认定不同模型能力等价：

| 工作类型 | 模型起点 | 推理强度起点 | 判据 |
|---|---|---|---|
| 按已批准结论同步文档、机械替换、简单既定验证 | GPT-5.6 Luna | Medium | 规则明确、低风险，结果可直接核验，无需诊断未知问题 |
| 方案已定的局部实现、沿用成熟模式的小改动 | GPT-5.6 Terra | Medium | 耦合低、失败影响有限，已有验证能覆盖关键行为 |
| 常规业务开发、跨文件修改、一般缺陷定位与修复 | GPT-5.6 Sol | Medium；跨层判断或较复杂诊断用 High | 契约明确，需要一定推理与行为验证；实际配置只选一个强度 |
| 架构取舍、复杂并发、持久化一致性、协议状态机、安全或数据丢失风险、高风险独立复核 | GPT-6 Astra | High；复杂探索或反证用 Extra High | 不确定性或失败代价高，需要跨模块推理和强验证；实际配置只选一个强度 |

5. **按实际判断负担选型**。文档中的架构设计、验证中的故障诊断可能需要更强模型，不能仅按文件类型、文件数量或“方案已定”选用较轻模型。规格完整、基线、复核与人工验收要求不随模型改变；不可用更强模型代替未决方案的细化。执行中发现隐藏耦合、风险扩大或现有方法无法形成可靠证据时重新评估配置，不按固定失败次数机械升级；配置建议本身不切换当前执行模型，实际更换沿用已有授权，缺少授权时才提交建议。
6. `Ultra` 的机制以当前客户端核实说明为准；若涉及自动委派，只有作者允许多代理协作且 Phase 适合独立并行时才推荐。建议配置本身不授予创建、分叉或委派任务的权限。
7. 选择理由只在不直观时用一句短话说明；模型更新后重新核对可用性与建议，不仅替换旧名称，也不因能力提升降低实施或验收门槛。成本判断包括返工和验证开销，不用 API 单价推断 Codex 套餐额度的节省比例。
