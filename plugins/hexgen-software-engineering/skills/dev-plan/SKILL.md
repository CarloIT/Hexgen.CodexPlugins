# dev-plan — 分阶段开发计划文档

产出一份**写给冷启动新会话 AI**的开发计划：作者为每个 Phase 开独立会话，并按计划选择 GPT 模型与推理强度。计划承载阶段目标、执行安排与进度；项目规则指定 `DESIGN.md` 等设计事实源时，路由到其**点名章节**。自包含指无需恢复旧会话或临时报告，执行者仍须核对本阶段涉及的当前源码、依赖与测试。全局协作规则沿用 AGENTS.md，不在技能中维护另一套。

## 核心原则（先理解为什么，再动笔）

1. **读者是冷启动的新会话**。每个可执行 Phase 就地写清做法、依赖、验证与完成定义；背景证据就地给出，或点名项目权威设计章节并复述关键不变量。不得依赖"见上文"、临时报告或会话外口头共识。自测法：从「通用守则 + 该章 + 点名设计章节」出发，执行者能否找到需核对的源码与测试，并判断开工条件是否满足？

2. **证据先于计划**。计划质量的上限是它背后核实工作的质量。每个"问题断言"必须带**可核查的来源指针**（代码 `文件:行号` / 设计文档章节 / 官方文档 URL / 实测记录）和核实日期；没核实过的不准写成事实，要么当场核实，要么显式标注「待核实 + 核实方法」。涉及代码行号的，写上行号免责条款（行号是某日基线，漂移后按符号名定位）——这让计划经得起代码演进。

3. **规格成熟度与模型能力分开**。可执行的实施 Phase 必须明确目标、契约、不变量、实施路径、失败边界与验收，不因模型更强而省略规格。尚待选择方案的部分标记「需细化」；可独立推进的已定内容拆为可执行 Phase。细节深度取决于任务风险和防止歧义的需要，模型配置按第 5 步选择。

4. **决策权属于作者**。凡是会改变公共契约、引入依赖、有商业/法律含义、或存在多个合理方案的点，列为「作者决策点」：写清选项、**建议值与理由**，由作者逐项拍板，并注明阻塞范围。批准后就地记录结论与日期，不留悬空选项；已批准且条件未变的事项不重复询问。项目指定设计事实源时，设计决策同步到该文档，PLAN.md 记录执行落点与章节指针。

5. **验证必须可执行**。写清命令、预期结果及需要覆盖的行为、边界和失败场景，例如「取消后任务退出，资源可重新获取」。记录实际通过、失败与跳过数，不设无依据的新增用例数量配额。完成定义逐项列出交付物和验收门槛；人工或发布验收属于本阶段时，证据未齐不得标记已完成，自动验证通过不代替作者签收。

6. **不静默丢弃任何输入**。审查报告、建议和旧待办逐条标记「采纳 / 暂缓 / 不采纳 / 已失效 / 重复合并」，写清理由与去向。采纳指向 Phase，暂缓进入 backlog，不采纳或已失效记录依据，重复项指向合并后的条目；不把所有未采纳意见都塞入 backlog。涉及取舍时仍按作者决策边界确认。

7. **路线图不是可执行 Phase**。分开记录三个维度：① 执行状态：🟪 未开始 / 🔄 进行中 / ✅ 已完成 / ⛔ 阻塞；② 规格成熟度：可执行 / 需细化；③ 范围属性：已纳入 / 可选。新会话实施须满足「可执行 + 已纳入 + 未开始」、完整章节、前置依赖已完成且成果可用、阻塞决策已批准；代码实施另须当前完整基线全绿（初始化例外）。进行中仅在作者明确续做时按同样门槛恢复；已完成不重做，阻塞先解阻，需细化先补规格，不得凭状态表或路线图摘要直接施工。

## 两类计划：先认清场景

写计划前先判断属于哪一类，它决定「基线」「证据」「首个 Phase」怎么写：

- **存量优化型**（基于现有代码做重构 / 修缺陷 / 优化）：近期可执行阶段在规划时实跑项目规定的完整构建与测试，记录到附录 C；纯路线图或文字更新可写「未运行 + 原因」，不据此升级规格成熟度或宣称可开工。每个代码实施阶段仍须先在当前代码上跑完整基线，全绿才动手；不绿立即停止实施并报告。证据 = `文件:行号` + 核实日期。
- **绿地起步型**（从零新建项目 / 模块）：**尚无代码，没有基线可跑**——首个 Phase 通常是「搭骨架 + 接底座 + 建立首个基线」，此后各 Phase 以它为对照原点；证据锚定**设计文档章节**（如 DESIGN.md §x）、官方文档或实测记录，而非代码行号；通用守则的「开工先跑基线」与开场提示词须给初始化 Phase 留例外（它没有上一手基线）。附录 C 如实写「绿地，基线由首个 Phase 建立」。

两者可在同一大项目里按 Phase 并存（如先绿地搭新模块、再优化既有模块）。裁剪通用守则时按各 Phase 的实际场景取舍，不要硬套不存在的基线。

## 工作流程

### 第 1 步：核实输入

- 收集本次计划的全部输入源：审查结论、需求描述、既有待办、他人建议文档。
- 对问题断言读码、查文档或实测核实，记录日期；基线是否实跑按上方计划类型处理。记录完整命令、实测结果与日期；未运行须说明原因，历史结果注明原日期，不冒充本次验证。规划基线不替代实施前基线，不修改命令、跳过失败或降低门槛来制造全绿。
- 输入中已失效/与现状矛盾的内容，修正后再用，并在交付时向作者指出（这经常发生：文档比代码老）。

### 第 2 步：确定文件位置与合并策略

- 计划文件位置遵守项目约定（很多项目的 AGENTS.md 会指定，如根目录 `PLAN.md`）；无约定时默认仓库根目录 `PLAN.md`。
- **动笔前先找既有计划文件并通读**：吸收其未完成待办与已完成台账进新计划，绝不让两份计划并行存在。
- 语言跟随项目文档语言（本用户默认中文）。

### 第 3 步：切分 Phase

- 粒度 = 一个新会话能完成且有独立验收结果的量（含基线、实现、验证、汇报）；不因模型增强机械扩大 Phase。
- 按实际依赖与风险安排顺序，不套用固定话题顺序；验证随所属 Phase 完成，不默认留到末尾集中补测试。
- 相关机械工作可合并；高风险改造独立成章并标注「高风险：先方案后实现」。已批准且条件未变的实施方案可直接引用，不重新走审批。
- 写清 Phase 间依赖（如"公共 API 定稿须在底座重构前"），没有依赖就标"无"，让作者可以并行开会话。
- 允许把远期、依赖尚不稳定的工作保留为「需细化」路线图，但每条至少写清阶段意图、当前最小依赖、范围属性（已纳入 / 可选）与细化触发条件；不得给路线图条目伪造可执行规格，也不得用「待细化」代替依赖。

### 第 4 步：按骨架填充

读取并套用 [references/template.md](references/template.md) 的完整骨架（文件头 / 开场提示词 / 通用守则 / 进度总览表 / Phase 章节 / 三个附录 / 已完成区）。开场提示词刻意置顶（紧邻文件头），方便作者每开一个 Phase 即来此复制。骨架中各占位符的填写要求都注释在模板里。

- 进度总览的「执行状态」格统一使用「图标 + 空格 + 中文状态」：🟪 未开始、🔄 进行中、✅ 已完成、⛔ 阻塞；阻塞时附一句原因。直接写入 Markdown 表格，不包行内代码，不使用纯文本、单独图标或任务复选框代替。新建计划与更新既有总览时均按此格式填写，状态判断仍遵守原有开工与验收门槛。
- 默认将新会话开场提示词视为作者粘贴到**已经手动创建的会话**的内容；不得仅因模型或推理强度建议要求执行 AI 再次创建、分叉或委派会话。若某个 Phase 确有隔离、并行或交接需求，将目标、授权边界、会话数量、工作区策略和汇总方式写入该 Phase，必要时列为作者决策点；通用开场提示词只路由到该约定，不重复或扩大授权。
- 可复制的开场提示词仅在首句出现一次 `Phase N`，后文统一称「本阶段」或「本阶段章节」，不再引入需替换的阶段编号占位符，让作者只改一次 `N`。

### 第 5 步：标注明确的模型与推理强度

1. 默认使用 **GPT-6 Astra**；仅在作者要求节省成本、指定其他模型或默认模型不可用时另行配置。模型不可用时说明限制并提交替代建议，不静默替换。
2. 用作者当前提供的列表或客户端可核实信息确认模型与强度；官方文档用于补充能力和机制，不能代替账号可用性证据。不写死档位清单，不把内部参数名当成界面名称；无法确认时标注不确定并请作者确认。
3. 每个 Phase 只写一行 **建议配置**：客户端模型短名称 + 可见强度，例如 `GPT-6 Astra / High`。进度总览合并到「建议模型」列，不另列强度、不写 slug；回退方案仅在作者要求时补充。
4. 下表是默认建议起点，按任务风险与复杂度调整，不是规格详略或验收强度的分档：

| 工作类型 | 模型策略 | 推理强度起点 | 判据 |
|---|---|---|---|
| 文档、骨架、机械清理、既定验证任务 | GPT-6 Astra | Medium | 方案已定，结果容易直接核验 |
| 算法、业务正确性、公共契约、UI/后端集成 | GPT-6 Astra | High | 需要跨文件判断和行为验证 |
| 架构、并发、持久化、协议状态机、安全或数据丢失风险 | GPT-6 Astra | Extra High | 失败代价高，需要探索、反证和强验证 |

5. 当前核实依据（2026-09-12，Codex 客户端 `models_cache.json`）：`Ultra` 的说明为最高推理并自动委派任务；使用时仍须核对当前说明。只有作者允许多代理协作且 Phase 适合独立并行时才推荐；建议配置本身不授予创建、分叉或委派任务的权限。
6. 选择理由只在不直观时用一句短话说明；模型更新后重新核对可用性与建议，不仅替换旧名称，也不因能力提升降低实施或验收门槛。

### 第 6 步：交付前自查

- [ ] 冷启动自测：从「通用守则 + 该章 + 点名设计章节」能否定位目标源码与测试，并核对全部开工条件？
- [ ] 每个问题断言都有 证据 + 核实日期，或显式「待核实」标记？
- [ ] 验证是否覆盖行为、边界和失败场景，包含命令与判断标准，且没有无依据的用例数量配额？
- [ ] 作者决策点是否附建议值、理由与阻塞范围？已批准结论是否记录日期、不重复询问，并按项目约定同步设计事实源？
- [ ] 每个 Phase 都用短名称写了「模型 / 客户端可见推理强度」？进度总览是否已合并到「建议模型」列、没有单列「推理强度」？是否删除了非必要的 slug、回退方案和重复理由？高风险 Phase 是否标注「先方案后实现」？
- [ ] 没有把 API 独占型号、内部参数名或用户客户端不可见的档位写进计划？
- [ ] 进度总览是否把「执行状态 / 规格成熟度 / 范围属性」分列，执行状态格是否统一为「🟪 未开始 / 🔄 进行中 / ✅ 已完成 / ⛔ 阻塞」的图标加文字格式，且阻塞附原因，没有纯文本、单独图标或任务复选框？
- [ ] 可执行行是否对应完整章节（目标、契约、不变量、实施路径、失败边界、依赖、验证与完成定义），且不依赖模型补齐未决方案？需细化条目是否明确细化触发条件？
- [ ] 所有输入是否都有处置、理由与去向，重复和失效项没有机械进入 backlog？
- [ ] 规划基线是否实跑并记录命令、结果、日期，或按允许场景注明未运行原因？是否仍明确实施前完整基线全绿及初始化例外？
- [ ] 开工是否检查前置依赖成果与阻塞决策，完成是否检查本阶段全部验收证据（包括适用的人工或发布验收）？
- [ ] 开场提示词只含「路由 + 硬约束」，细节单点维护在计划内，且可复制内容仅首句含一次 `Phase N`、没有其它需替换的阶段编号占位符？
- [ ] 开场提示词是否明确拦截「需细化」路线图，禁止执行会话根据一行摘要直接写代码？
- [ ] git 等敏感操作的归属（默认：由作者人工主导，AI 只交提交信息草稿）与项目/全局规则一致？
- [ ] 文件位置与语言符合项目约定，且不存在并行的旧计划？

交付时除了计划文件本身，在回复中给出：① 各 Phase 的简短建议配置一览；② 开场提示词全文（方便作者立即复制）；③ 核实输入时发现的与现状不符之处。模型来源和回退方案仅在用户要求或存在不确定性时补充。
